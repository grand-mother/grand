# `dev-next` paperwork

Everything that describes the state of the `dev-next` recovery: the plan, the
branch record, and the two diagrams. Five of these six files are generated —
edit the generator, not the file.

## What is here

| File | What it is | Generated by |
|---|---|---|
| [`RECOVERY_PLAN.md`](RECOVERY_PLAN.md) | The plan. Phases, decisions, corrections, open questions. **Hand-written**, updated in the same commits as the work it describes. | — |
| [`BRANCHES.md`](BRANCHES.md) | Every branch **that exists today**: who made it, what it came off, what came out of it, and whether it should be merged. | `docs/dev/make_branch_inventory.py` |
| [`branches.svg`](branches.svg) | The same branches as a family tree. Columns are generations. | `docs/dev/make_branch_diagram.py` |
| [`recovery.svg`](recovery.svg) | How far the repair has got, phase by phase. Read from the plan's own checkboxes. | `docs/dev/make_recovery_diagram.py` |
| [`history.svg`](history.svg) | Every branch and merge since 2019, on a time axis. Context, not a working document. | `docs/dev/make_history_diagram.py` |
| `README.md` | This file. | — |

`RECOVERY_PLAN.md` embeds both diagrams and links `BRANCHES.md`, so reading the
plan is reading all of it. The plan is also rendered as the documentation's
[roadmap page](../../../docs/source/roadmap.rst), which `.. include::`s this
same file — there is one copy, and it is this one.

## Regenerating

From the repository root, in an environment with `grand` importable:

```bash
python docs/dev/make_branch_inventory.py
python docs/dev/make_branch_diagram.py
python docs/dev/make_recovery_diagram.py
python docs/dev/make_history_diagram.py
```

Each prints what it wrote. None of them takes an argument, and all four are
safe to re-run: they overwrite in place and read the repository as it stands.

**Commit the script before regenerating.** Each output stamps the commit of the
generator that made it, and an uncommitted generator stamps
`uncommitted (modified since)` — which is accurate, and useless in a document
somebody is meant to trust six months from now.

**Snapshot before a deck release.** The diagrams are regenerated on every merge,
so a slide pointing at the live name silently shows today's picture instead of
what was presented. Copy them to `figures/releases/` first — see the deck's own
notes.

## Which document answers which question

- *What should we do about branch X?* — `BRANCHES.md`, then `branches.svg`.
  Live branches only: this is a document to act on, and a branch that no longer
  exists cannot be acted on.
- *How far along is the repair?* — `recovery.svg` and the plan.
- *How did the repository get like this?* — `history.svg`. It draws all 69
  branches the repository has ever had, including the 31 that were merged and
  deleted, recovered from the merges that took them. Nothing in it is meant to
  be acted on.

`recovery.svg` used to show the merge queue too. It does not any more:
`branches.svg` shows every branch with more detail and reads it from git, and
two pictures of the same thing is how the queue here came to show a decision as
blocked three days after it was settled.

## Why each diagram is written twice

`branches.svg` and `recovery.svg` are written here *and* to `docs/source/`,
because the plan embeds them and
is read in two places that resolve relative paths differently: GitHub resolves
an image beside the file it appears in, Sphinx relative to `docs/source/`, and
no single relative path satisfies both. One script writes both copies, so they
cannot drift. Do not hand-copy them. `history.svg` is written here only — the
plan does not embed it.

## Editing

Almost everything in the two branch documents is read from git — dates, authors,
commit counts, parentage, and whether a branch is contained in the trunk. Those
cannot be edited and should not need to be. Three things are not read from git,
and all three live in **[`docs/dev/branch_facts.py`](../../../docs/dev/branch_facts.py)**,
which both branch generators import:

- **`DESCRIPTIONS`** — two to four words per branch. A branch with no entry is
  still listed, with an empty description, so a newly pushed branch appears
  immediately rather than waiting to be noticed.
- **`SHORT`** — an abbreviation for a name too long to fit a diagram box.
  Display only; git is always asked about the real name, so an abbreviation
  here cannot break a lookup. It did once.
- **`VERDICTS`** — whether an unmerged branch should be merged, and why. The
  one part of these documents that is an opinion rather than a measurement.
  Set `VERDICTS_REVIEWED` to the date when they were last gone through end to
  end; `BRANCHES.md` prints it, so a stale opinion is visible as stale.

To add a branch verdict, add an entry to `VERDICTS` keyed by the exact branch
name, as `(action, reason)`. The actions are `merge`, `merge-hand`,
`cherry-pick`, `no`, `decide` and `ask`; `make_branch_inventory.py` maps them to
the words that appear in the document. A branch with no entry is reported as
*not yet reviewed*, which is honest and is meant to be uncomfortable.

The diagram **refuses to build** rather than clip a label that will not fit its
box. If it exits with a complaint about a name, add a `SHORT` entry; do not
widen the box without checking the columns still fit.

## Conventions

- 🟢 green: contained in `dev-next`. 🟡 amber: still carrying its own patches,
  and what to do about it is an **open question**. 🔴 red: decided against — it
  will never be merged. 🟣 purple: its **content** is in the trunk, rewritten or
  moved, but its patch is not and never will be. 🔵 blue: the trunk. Grey, in
  `history.svg` only: merged and since deleted. The same colours as the
  diagrams; Markdown has no colour of its own, so the documents use the
  circles, which survive copy-paste.
- Purple exists because `git cherry` compares patch identity. A paragraph
  rewritten into another file matches nothing, so such a branch reads as
  unmerged for ever. Green would claim the patch is contained and red would
  claim the work was rejected; both are false, and the question a reader has is
  whether the work was lost. `tian-conda-arm` is the first: ten lines of ARM
  notes, rewritten into `docs/source/installation.rst`.
- The amber/red split is the difference between a question nobody has answered
  and one that has been closed. A verdict in `VERDICTS` is a recommendation; an
  entry in `DECIDED` is what turns a branch red. Add one only when the decision
  has actually been taken.
- **To record a decision**, add to `DECIDED` in `docs/dev/branch_facts.py`:
  `"branch-name": ("YYYY-MM-DD", "one line saying why")`, and regenerate. The
  date and the line appear in the *Decisions taken* table at the top of
  `BRANCHES.md`, which is the running log — it is generated, so it cannot fall
  out of step with the colours.
- *Commits* counts everything on a branch since it diverged. *Own* counts the
  patches that are in no other branch. For an old branch these can be very
  different numbers — `snonis_sim2root_test_merge` has 279 and 2 — and *Own* is
  the one a merge decision turns on.
