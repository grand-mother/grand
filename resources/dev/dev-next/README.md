# `dev-next` paperwork

Everything that describes the state of the `dev-next` recovery: the plan, the
branch record, and the two diagrams. Four of these five files are generated —
edit the generator, not the file.

## What is here

| File | What it is | Generated by |
|---|---|---|
| [`RECOVERY_PLAN.md`](RECOVERY_PLAN.md) | The plan. Phases, decisions, corrections, open questions. **Hand-written**, updated in the same commits as the work it describes. | — |
| [`BRANCHES.md`](BRANCHES.md) | Every branch the repository has ever had, live or merged-and-deleted: who made it, what it came off, what came out of it, and whether it should be merged. | `docs/dev/make_branch_inventory.py` |
| [`branches.svg`](branches.svg) | The same thing as a family tree. Columns are generations. | `docs/dev/make_branch_diagram.py` |
| [`recovery.svg`](recovery.svg) | The merge queue and the phases. | `docs/dev/make_recovery_diagram.py` |
| `README.md` | This file. | — |

`RECOVERY_PLAN.md` embeds both diagrams and links `BRANCHES.md`, so reading the
plan is reading all of it. The plan is also rendered as the documentation's
[roadmap page](../../../docs/source/roadmap.rst), which `.. include::`s this
same file — there is one copy, and it is this one.

## Regenerating

From the repository root, in an environment with `grand` importable:

```bash
python docs/dev/make_branch_inventory.py
python docs/dev/make_branch_diagram.py
python docs/dev/make_recovery_diagram.py
```

Each prints what it wrote. None of them takes an argument, and all three are
safe to re-run: they overwrite in place and read the repository as it stands.

**Commit the script before regenerating.** Each output stamps the commit of the
generator that made it, and an uncommitted generator stamps
`uncommitted (modified since)` — which is accurate, and useless in a document
somebody is meant to trust six months from now.

**Snapshot before a deck release.** The diagrams are regenerated on every merge,
so a slide pointing at the live name silently shows today's picture instead of
what was presented. Copy them to `figures/releases/` first — see the deck's own
notes.

## Why each diagram is written twice

Both diagrams are written here *and* to `docs/source/`. The plan embeds them and
is read in two places that resolve relative paths differently: GitHub resolves
an image beside the file it appears in, Sphinx relative to `docs/source/`, and
no single relative path satisfies both. One script writes both copies, so they
cannot drift. Do not hand-copy them.

## Editing

Almost everything in the two branch documents is read from git — dates, authors,
commit counts, parentage, and whether a branch is contained in the trunk. Those
cannot be edited and should not need to be. Three things are not read from git,
and all three live in **[`docs/dev/branch_facts.py`](../../../docs/dev/branch_facts.py)**,
which both branch generators import:

- **`DESCRIPTIONS`** — two to four words per branch. A branch with no entry is
  still listed, with an empty description, so a newly pushed branch appears
  immediately rather than waiting to be noticed.
- **`SHORT`** — an abbreviation for a name too long to fit a diagram box.
  Display only; git is always asked about the real name, so an abbreviation
  here cannot break a lookup. It did once.
- **`VERDICTS`** — whether an unmerged branch should be merged, and why. The
  one part of these documents that is an opinion rather than a measurement.
  Set `VERDICTS_REVIEWED` to the date when they were last gone through end to
  end; `BRANCHES.md` prints it, so a stale opinion is visible as stale.

To add a branch verdict, add an entry to `VERDICTS` keyed by the exact branch
name, as `(action, reason)`. The actions are `merge`, `merge-hand`,
`cherry-pick`, `no`, `decide` and `ask`; `make_branch_inventory.py` maps them to
the words that appear in the document. A branch with no entry is reported as
*not yet reviewed*, which is honest and is meant to be uncomfortable.

The diagram **refuses to build** rather than clip a label that will not fit its
box. If it exits with a complaint about a name, add a `SHORT` entry; do not
widen the box without checking the columns still fit.

## Conventions

- 🟢 green: contained in `dev-next`. 🟡 amber: still carrying its own patches.
  🔵 blue: the trunk. The same colours as the diagram; Markdown has no colour of
  its own, so the documents use the circles, which survive copy-paste.
- *Commits* counts everything on a branch since it diverged. *Own* counts the
  patches that are in no other branch. For an old branch these are very
  different numbers — `beta_dc1` has 333 and 3 — and *Own* is the one a merge
  decision turns on.
